# Mekong Delta Living Lab

Interactive web maps for monitoring mangrove dynamics in the Mekong Delta, Vietnam (1988–2026).

## Features

| Map      | Description                     |
| -------- | ------------------------------- |
| Coverage | Mangrove extent by year         |
| Gain     | Expansion and restoration areas |
| Loss     | Deforestation hotspots          |

Includes sea dikes, breakwaters, and commune boundaries with bilingual support (EN/VI).

## Google Earth Engine setup

Every map is generated by calling Google Earth Engine (GEE) from Python, so you need
a Google account with Earth Engine access before anything else works.

1. Sign up / confirm access at [code.earthengine.google.com](https://code.earthengine.google.com).
2. Have (or create) a Google Cloud project with the Earth Engine API enabled.
   The scripts default to project id `gee-mekong-map` — if you don't have access
   to that project, use your own by setting the `GEE_PROJECT` environment
   variable to your project id.
3. Install dependencies:

   ```bash
   pip install -r requirements.txt
   ```

4. Run any notebook (`MAP01_Mangrove_LOSS.ipynb`, `MAP02_Mangrove_GAIN.ipynb`,
   `MAP03_Mangrove_COVERAGE.ipynb`). The first cell imports
   [`GEN01_GEE_Authenticate.py`](GEN01_GEE_Authenticate.py), which:
   - detects it's running locally (no `GEE_SERVICE_ACCOUNT`/`key.json`),
   - opens a browser via `ee.Authenticate()` to sign in with your Google account,
   - calls `ee.Initialize(project=GEE_PROJECT)`,
   - runs a small test call and prints `Connected to Google Earth Engine (...)`
     to confirm the connection actually works before generating any map.

   If it raises `Google Earth Engine connection failed`, it means the signed-in
   account doesn't have Earth Engine access to that project — fix access in the
   Cloud Console (or switch `GEE_PROJECT`) and rerun.

No other manual editing is needed — `GEN01_GEE_Authenticate.py` picks local vs.
CI mode automatically.

## Running locally

```bash
pip install -r requirements.txt
```

Then open and run `MAP01_Mangrove_LOSS.ipynb`, `MAP02_Mangrove_GAIN.ipynb`, or
`MAP03_Mangrove_COVERAGE.ipynb` top to bottom in Jupyter/VS Code. Each notebook
authenticates with GEE (see above) and writes its output to
`Mangrove_<LOSS|GAIN|COVERAGE>_map.html` in the repo root, which `index.html`
loads directly — no build step needed to preview the site, just open
`index.html` in a browser after regenerating the map(s) you changed.

## CI / GitHub Actions setup

The three workflows in [`.github/workflows/`](.github/workflows) regenerate the
maps on a schedule and push the updated HTML back to `main`. They authenticate
with a **service account** instead of an interactive login, via two repo
secrets (Settings → Secrets and variables → Actions):

| Secret               | Value                                                              |
| -------------------- | ------------------------------------------------------------------- |
| `GEE_SERVICE_ACCOUNT` | Service account email, e.g. `name@project-id.iam.gserviceaccount.com` |
| `GEE_KEY`             | The full contents of that service account's JSON key file           |

To create a service account with Earth Engine access:

1. In [Google Cloud Console](https://console.cloud.google.com/iam-admin/serviceaccounts),
   create a service account under the Earth Engine-enabled project.
2. Grant it the **Earth Engine Resource Writer** (or Viewer, if it only reads
   public datasets like this project does) role.
3. Register it for Earth Engine at
   [signup.earthengine.google.com](https://signup.earthengine.google.com/#!/service_accounts).
4. Create a JSON key for it and paste its full contents into the `GEE_KEY` secret.

The workflow writes that secret to `key.json` on the runner at build time — it
is never committed (see [`.gitignore`](.gitignore)). With both secrets set,
`GEN01_GEE_Authenticate.py` automatically uses the service account branch
instead of the interactive login.

## Legend color ramps

The LOSS and GAIN legends use one color per time interval (e.g. "2020-2025").
Those colors are generated, not hand-picked: [`GEN04_mangrove_layers.py`](GEN04_mangrove_layers.py)
builds each ramp as evenly spaced OKLCH lightness steps on a single hue
(purple for loss, green for gain), so every interval stays visually
distinguishable from its neighbors and legible against the map's white
legend box, no matter how many intervals get added over time.

This replaced an earlier version that reused a standard ColorBrewer
`BuPu`/`BuGn` swatch set, which broke once a 9th interval (2025-2026) was
added: the lightest step became nearly invisible against the legend
background (WCAG contrast ~1:1, need ≥ 2:1) and the two lightest steps were
nearly indistinguishable from each other.

If you add another interval (e.g. once 2030 exists), bump `n_classes` in the
`_sequential_ramp(...)` calls in `GEN04_mangrove_layers.py` and re-check the
new ramp — if it's ever borderline, widen `l_floor`/`l_ceil` or lower
`chroma` slightly and regenerate.
